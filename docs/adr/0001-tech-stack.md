# ADR-0001: Tech stack for the OSR checklist

- **Status:** Proposed
- **Date:** 2026-10-25
- **Related:** [Design](../superpowers/specs/2026-10-25-osr-checklist-design.md)

## Context

We are building a read-only reference website that tells sailors which equipment a
monohull needs to race under World Sailing Offshore Special Regulations (OSR)
categories 2, 3, 3 with liferaft, and 4. Every item links back to its source in the
official World Sailing PDF.

Forces:

- **Content, not behaviour.** A few hundred items per edition, each with a name,
  plain-language explanation (EN + DE), a drawing, OSR rule numbers, applicable
  categories and PDF page references. No accounts, no saved state, no server logic.
- **Rare updates.** A new OSR edition every two years, plus occasional mid-cycle
  versions (e.g. 2026-2027 V2, effective 2027-01-01). Multiple editions are shown
  side by side via a dropdown.
- **Source PDFs are hard to parse.** World Sailing publishes one extract PDF per
  category (`Extract-Mo2…`, `Mo3`, `Mo3Life`, `Mo4`). Text extraction scrambles the
  margin category codes (`MoMu0,1,2,3`) relative to rule numbers, so a
  deterministic parser is brittle. An LLM reading the PDF directly handles this well,
  and the job runs only a few times per edition cycle.
- **Phone and desktop.** Must be comfortable on a phone at the dock and on a desktop.
- **Hosting options available:** GitHub Pages (static only), or a personal vServer.
- **Copyright.** The OSR text is © ORC Ltd / World Sailing; reprinting requires
  permission. We therefore link to the official PDFs and write our own explanations;
  no verbatim regulation text in v1.

## Decision

1. **Static site generated with [Astro](https://astro.build)** (TypeScript), using
   content collections with Zod schemas so that malformed content (missing category,
   missing source page, unknown section) fails the build.
2. **Content lives in the repository as data files** (YAML), one file per item plus
   one manifest per edition. Fixing an item is a one-file edit and a normal PR.
3. **Fully pre-rendered pages per language × edition × category**
   (e.g. `/de/2027-v2/osr3/`). Filtering happens at build time, so the site needs
   no client-side framework; a few lines of vanilla JS only drive the dropdown
   navigation.
4. **Built-in Astro i18n routing** for English and German.
5. **Hosting on GitHub Pages**, deployed by a GitHub Actions workflow on every push
   to `main`.
6. **LLM-based extraction as a manually triggered GitHub Actions workflow** that
   calls the OpenAI API (owner's choice), writes data files, and **opens a pull request** for human
   review. It never publishes directly. Drawings (SVG) and EN/DE explanations are
   generated in the same pipeline, only for new or changed items.
7. **Drawings are SVG line drawings generated by the LLM**, committed to the repo,
   text-free (language-neutral), styled with `currentColor` so they work in light and
   dark mode. Any drawing can later be replaced by a photo.

## Alternatives considered

| Option | Why not (for now) |
|---|---|
| Hand-written HTML | Unmaintainable at hundreds of items × 2 languages × several editions. |
| Eleventy / Hugo | Equally viable. Astro chosen for typed content collections (build-time validation of the safety-relevant data) and first-class i18n. |
| SPA (React/Vue) with client-side filtering | Adds a framework and a JS bundle for no user-visible gain; pre-rendered pages are faster on a phone and shareable by URL. |
| Full app on the vServer (backend + DB) | Only justified once there is per-user state (tick-off, boat profiles). Not in scope. Astro can later add client-side islands with browser storage before a server is ever needed. |
| Deterministic PDF parser (pdftotext + regex) | Column scrambling of category codes makes it fragile; would need rework every edition. |
| Separate image-generation service | Second API/account, inconsistent style, raster files; LLM-written SVG is enough for schematic equipment drawings. |
| Offline / PWA | Not needed for v1. Can be added later with a service worker without changing the architecture. |

## Consequences

- **+** Zero running cost and zero server maintenance; nothing to patch.
- **+** Every content change is reviewable as a git diff; a new edition's PR doubles
  as a "what changed" list.
- **+** Build-time schema validation guards against incomplete data.
- **−** LLM output can be wrong (especially category applicability). Mitigated by the
  PR review step and by cross-checking against all four category extracts
  (see design). Final responsibility for correctness stays with a human reviewer.
- **−** The extraction workflow needs an OpenAI API key stored as a GitHub
  Actions secret; each run has a small API cost.
- **−** `#page=N` deep links into PDFs are honoured by desktop browsers but often
  ignored by mobile PDF viewers. The page number is therefore always shown as text
  next to the link.
- **−** Pre-rendering every combination multiplies page count
  (2 languages × editions × 4 categories). At this size (tens of pages) that is
  negligible.
